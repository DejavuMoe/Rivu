# 界面设计走查（2026-11-19）

这份走查回答：按「分层的设计系统」来看，Rivu 的界面现在做到了哪一层、缺什么、下一步改什么。改进项列在最后的清单里，[`../roadmap.md`](../roadmap.md) 的「界面打磨」引用其中标「发布前」的项。

## 怎么查的

- **数代码**：统计 `apps/dashboard/src` 里 77 个样式文件实际用到的颜色、字号、字重、间距、圆角、线宽、阴影、层级、断点，再和 [`DESIGN.md`](../../apps/dashboard/DESIGN.md) 的规则比。
- **看渲染结果**：构建主原型，把站点列表、看板、接入诊断、设置、账号页渲染出来看，浅色和深色各一遍，桌面宽度（1440）和手机宽度（390）各一遍。
- **比原型和生产**：逐个文件比较 `designs/rivu-svelte` 和 `apps/dashboard`。

没做的：没有在真实手机上看，没有用屏幕阅读器走一遍，没有测真实数据量下的图表。渲染是把页面打印成 PDF 看的，趋势图的宽度在这种方式下不准，所以这次没有评价趋势图的布局。

## 结论

1. **地基是好的。** 颜色有两级（Radix 色阶到语义令牌），深浅色只在一处切换；颜色、字号、字重在组件里 100% 走令牌。这是多数项目做不到的。
2. **规则原来只靠自觉。** 这次之前没有任何工具检查这些规则，也没有东西保证原型和生产是同一套。现在补上了（见「工程化」）。
3. **越往上层越薄。** 令牌和组件扎实；「范式」（完成一件事的最小界面单位）和「决策」（什么时候用什么）基本没有写下来，靠的是照着已有页面仿写。页面自己写的样式比共享组件里的还多。
4. **有几处直接影响观感和理解**，最明显的是浅色模式下条形图几乎看不见。

## 工程化：这次补上的

| 做了什么 | 在哪 | 管什么 |
|---|---|---|
| 设计规则检查 | [`tools/design-lint/check.mjs`](../../tools/design-lint/check.mjs)，`node tools/design-lint/check.mjs` | 裸色值、字号、字重、线宽、圆角、阴影、渐变、动效时长、中点分隔符。违反就失败，例外要在代码旁边写明原因 |
| 原型与生产同步检查 | 同上 | 令牌文件和共享组件在两边必须逐字节相同 |

还没有的：

- **截图对比**。改了样式之后，没有自动的办法知道哪些页面变了。采集脚本已经在 CI 里用 Playwright，可以复用它给主原型截图（几个关键页面 × 两个主题 × 两个宽度）。
- **无障碍自动检查**。对比度、标签、焦点顺序目前靠人看。
- **组件一览页**。主原型的评审面板能切换页面的状态，但看不到单个组件的全部尺寸和状态。

### 周报

**已定并确认（2026-11-19）**：订阅入口放在账号页；邮箱确认改成点邮件里的链接。主原型按这个改好，外观和文案已确认，按它实现。

原来的做法是每个站点的设置里各有一页，订阅前要把邮件里 43 个字符的确认码粘贴回页面。改的理由：

1. **确认方式**。粘贴 43 个字符是整个产品里最重的一步操作。重设密码、接受邀请、退订都已经是「点邮件里的链接，再点一次按钮」，订阅用同一种方式。
2. **放在哪**。收不收周报是个人偏好。放在站点设置里，有 5 个站点的人要进 5 次设置页、确认 5 次邮箱；而且点「取消订阅」会连邮箱确认一起清掉，误点之后要重新走一遍。放在账号页，一张卡片列出所有能看的站点，每行一个开关，邮箱只确认一次。

新流程在主原型里是这样的：

| 状态 | 账号页「邮件周报」卡片显示什么 |
|---|---|
| 邮箱没确认 | 接收邮箱、周报内容，一个「发送确认邮件」按钮 |
| 等待确认 | 「确认邮件已发到某某邮箱，点邮件里的链接」；可以重新发送（一分钟一次）或取消 |
| 邮箱已确认 | 所有能看的站点，每行一个开关，旁边是这个站点的发送时间；开关立刻生效 |
| 确认邮件没发出去 | 留在原来的状态，卡片里一条错误提示 |
| 实例没配置邮件 | 邮箱没确认的人看不到这张卡片；已确认的人看到「周报暂停发送」，开关照常可用 |

邮件里的链接打开的是一个独立页面，不需要登录：打开只显示说明，点「确认邮箱」才生效，这样邮件客户端预览链接时不会替用户确认。链接过期或用过时，页面指回账号页重新发送。

**后台跟着改了这些**（已完成，接口说明见 `docs/architecture/platform-and-ops.md` 的「周报订阅接口」）：

- 邮箱确认从「每个站点一次、粘贴确认码」改成「每个账号一次、点链接」。确认邮件里放链接；令牌只能用一次、有期限、数据库里只存哈希；打开链接不生效，提交才生效。
- 新增读取接口：这个账号的邮箱是否已确认，以及所有能看的站点和各自是否订阅、时区、每周起始日。
- 新增按站点开关的接口；要求邮箱已确认。
- 关掉某个站点、点邮件里的退订链接，都只关那一个站点，不清邮箱确认。
- 确认邮件发送失败时不改变状态（现在是先存下新确认码再报错）。
- 失去站点访问权时删除对应订阅：现有行为，保留。
- 已经订阅的用户（旧流程确认过的）视为邮箱已确认。

旧流程的独立设置页原型已删除，`designs/weekly-report/` 现在只放邮件。邮件的排版是路线图里单独的一项，还待确认。

### 决策表草案

下面是参照现有页面的做法拟的，**还没有生效**，个别行可能和现状不完全一致，审的时候一并核对。你看过之后再并入 `DESIGN.md`。

**出了结果，怎么告诉用户**

| 情况 | 用什么 |
|---|---|
| 操作成功，结果在页面上已经看得见（列表多了一行、开关变了） | 一条短通知，或者不提示 |
| 某个字段填错了 | 写在这个字段下面 |
| 有一个问题会一直存在，需要用户处理（邮件服务不可用、确认邮件没发出） | 卡片里的提示条，只用警告和错误两种 |
| 一块数据加载失败 | 这一块的位置显示原因和「重试」，其他部分照常 |
| 整个应用连不上服务器 | 整页只显示这一件事 |

**一个设置放在哪**

| 影响谁 | 放哪 |
|---|---|
| 所有看这个站点的人看到的数据 | 站点设置 |
| 只影响我自己 | 账号 |
| 影响组织里的人 | 组织 |

**改完要不要点保存**

| 情况 | 做法 |
|---|---|
| 开关 | 立刻生效 |
| 文字，或者几个字段要一起生效 | 有改动时才出现「保存」和「还原」 |

**要不要二次确认**

| 后果 | 做法 |
|---|---|
| 可以再做一次改回来（取消订阅、撤销邀请） | 不确认 |
| 改不回来，影响范围小（撤销一个 API 密钥、删除一条共享链接） | 对话框确认一次 |
| 改不回来，影响范围大（删除统计数据、删除站点） | 对话框里输入站点名称 |
